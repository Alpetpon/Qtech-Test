
# Сервис рассылок поставщикам и разбор полученных предложений

Задача:  
Cоздать MVP сервиса, который отбирает поставщиков по статусу, рассылает им запрос прайса через очередь с паузами и лимитом, разбирает ответы моделью и показывает отчет по рассылкам

Стек: Python 3.13, FastAPI, SQLAlchemy, Alembic, PostgreSQL 16, React + Vite, Docker Compose.  

## Запуск

Нужны Docker с Compose 2.24+ и bash (macOS, Linux; на Windows — из WSL, см. пункт «Ограничения»).

```bash
./start.sh
```

- Логи: `docker compose logs -f`
- Остановить: `docker compose down`
- Начать с чистой базы и со времени, указанного в задании: `docker compose down -v`, затем `./start.sh`

Без скрипта:

```bash
cp .env.example .env
docker compose up --build -d
```


## Тесты

Все команды выполняются из корня репозитория. Нужен файл `.env`: его создает `./start.sh`, или его можно создать командой `cp .env.example .env`.

**Бэкенд** содержит 308 тестов, выполняется около 15 секунд после сборки образа, без выхода в сеть:

```bash
docker compose run --rm --build tests
```

Тесты идут на своей базе (`test-db`, данные хранятся в памяти) в сети без выхода наружу, модель отвечает по записанным ответам, часы подменены. Сквозной сценарий `backend/tests/scenario/test_spec_data.py`  прогоняет 17 дней рассылки на данных задания и на полном наборе, с `RATE_LIMIT` и перезапуском воркера посреди паузы. После прогона `test-db` остается запущенной; `docker compose --profile test down` останавливает ее вместе со всем стеком, данные основной базы сохраняются.

**Точность модели** пересчитывается по записанным ответам, без сети и без ключа; итог сохраняется в `eval/results.md`:

```bash
docker compose run --rm --no-deps --build -v ./eval:/app/eval app python -m scripts.eval_llm
```

С флагом `--record` скрипт обращается к настоящей модели (нужен `LLM_API_KEY`) и перезаписывает `eval/recordings/`.

**E2E в браузере.** Playwright, нужен Node.js 22+:

```bash
cd frontend && npm ci && npx playwright install chromium webkit && npm run e2e
```

Сценарии (каждый — в Chromium и WebKit):
- рассылка от запуска до кнопки «Применить» с перемоткой часов;
- пустой менеджер вписывают в превью, и рассылка запускается.

Для тестов поднимается отдельный стек – проект compose `qtech-e2e` на порту 8023 (`E2E_PORT`):
- перед каждым тестом база чистая;
- данные только из задания, без `data/extra/`;
- без ключа модели и без `RATE_LIMIT`.

После прогона стек удаляется, основной стек и его база не затрагиваются.



## Решения и допущения

### Ловушки во входных данных

Данные задания лежат в `data/` без изменений, новые добавленные данные лежат отдельно в `data/extra/` с теми же именами файлов; при запуске  загрузчик читает обе папки. Справочник ников `supplier_contacts.json` создан новый, потому что в задании нет связи ник → поставщик, а без нее в общем чате c3 не понять, ответила Kestrel Foods или Kestrel Foods EU. Ники привязаны по смыслу; в `data/` лежат ники из задания, в `data/extra/` лежат ники расширения.  
  
Формальных ошибок в задании не нашел, были найдены только смысловые ошибки

### Очередь и надежность

- **Одно сообщение на чат.** При запуске рассылка кладет в очередь `outbox` по строке на чат с уже подставленным текстом; пара «рассылка, чат» считается уникальной. Создание рассылки идет под блокировкой в базе, поэтому два одновременных запуска не поставят чат в очередь дважды. Чат, который стоит в очереди другой рассылки, исключается.
- **Темп.** Сообщения уходят по одному с общего аккаунта `@company_shared`, между отправками используется случайная пауза 60–180 с. Лимит используем 100 сообщений за прощедщие 24 часа, а не за календарные сутки.
- **Без повторов после перезапуска.** Перед вызовом отправителя строка получает статус `sending`, и это сохраняется в базе. После отправки статус `sent`, время отправки, `last_outbound_at` чата и статус поставщика пишутся одной транзакцией. 
- **Падение посреди отправки.** Если воркер упал между `sending` и записью результата, неизвестно, ушло ли сообщение. При старте воркер помечает такие сообщения `unknown` и повторно не отправляет(было принят решение, что лучше появится одно потерянное сообщение, которое админ проверит и допишет руками, чем получим дубль в чате поставщика) Дальше `unknown` считается отправленным в момент восстановления. last_outbound_at` не меняется.
- **Один отправитель.** Отправка идет под блокировкой аккаунта в Postgres вместе с вызовом заглушки. Даже если запустить два воркера, они не отправят одновременно и не привыстя лимит.
- **Пауза на `RATE_LIMIT`.** Ошибку получает аккаунт, а он один, поэтому на паузу встают все рассылки сразу. Сообщение, на котором пришла ошибка, считается неотправленным: оно возвращается в начало очереди, в суточный лимит не попадает, дата последней отправки в чат не меняется. Через 15 минут (`RATE_LIMIT_PAUSE`) очередь продолжает сама, либо чтобы не ждать,  есть кнопка «Продолжить» на странице рассылки. Новый `RATE_LIMIT` ставит новую паузу на тот же срок. Пауза хранится в базе, поэтому переживает перезапуск воркера.

### LLM

- **Модель.** OpenRouter (OpenAI-совместимый API), `anthropic/claude-sonnet-5.5`. Ключ — `LLM_API_KEY`, модель — `LLM_MODEL`. Ответ модели — JSON по строгой схеме.
- **Промпт** — [`prompts/reply_analysis.md`](prompts/reply_analysis.md). Предложением считаем только ответ с ценой: «прайс во вложении» считаем за `offer`, а «перчатки есть, сколько нужно?» или «пришлем прайс позже» относим в `other`. Отказ без замены считаем `refusal`.  Также есть правила для полей, для ответа из нескольких сообщений, пометки и три примера.
- **Защита от инструкций в ответе.** Текст поставщика стоит между `<reply>` и `</reply>`, а сами эти теги из текста вырезаются. Промпт указывает считать текст данными, а не командами, если поставщик пишет что-то вроде «игнорируй правила», модель ставит пометку «проверьте вручную». Это проверяет размеченный случай `injection`.
- **Проверка ответа модели** (`backend/app/llm/validation.py`). Модели не верим на слово, каждое поле сверяем с текстом поставщика:
  - ответ не JSON по схеме, переспрашиваем один раз с описанием ошибки; не вышло, значит уходит в  `other` с пометкой «проверить вручную»;
  - цена больше нуля и встречается в тексте числом: понимаем «1 250,50», «1,250.50», «50k», а размеры вида 40x30x30 не берем;
  - партия — целое больше нуля и тоже есть в тексте; срок — целое больше нуля;
  - валюта — из списка ISO 4217; цена без валюты получает пометку для проверки;
  - у `refusal` и `other` поля предложения очищаются, `offer` без единой позиции, получает статус «проверить вручную»;
  - подсказку поставщика принимаем, только если он есть в переданном списке.

  Что не прошло проверку, остается пустым, а причина видна в отчете, админ вписывает значение сам.  

- **Записанные ответы.** Запись ищется по хешу запроса: модель, промпт, схема и текст. Тесты и воркер без ключа берут записи из `backend/tests/fixtures/llm/`, оценка — из `eval/recordings/`. Правка промпта или модели требует перезаписи:
  `docker compose run --rm --no-deps --build -v ./backend/tests:/app/tests app python -m app.llm.record tests/fixtures/llm` (необходим ключ openrouter).
- **Точность** — [`eval/results.md`](eval/results.md). Было размечено  17 ответов: 4 из данных задания, 6 из `data/extra/` и 7 придумал под точечные случаи( встречное предложение, две позиции в одном ответе, опечатки, вежливый и временный отказ, вопрос без цены, попытка подсказать модели ответ).  
Результат: тип ответа — 17/17, тип и все поля — 17/17, проверка ничего не отклонила.

  Выборка маленькая: 0 ошибок из 17 не означает, что модель никогда не ошибается.  
По правилу трех (если ошибок 0 из n, их доля с вероятностью 95% не выше 3/n) можно сказать лишь, что модель ошибается, скорее всего, реже чем в 18% случаев.

### Время

- Время, указанное в задании,  2026-11-01T10:00:00Z (`CLOCK_START`). Текущее время не берем из системных часов, `now()` в Postgres тоже не используем. Часы хранятся в базе одной строкой: время задания, реальный момент первого запуска и накопленная перемотка. Текущее время = время задания + реальное время с первого запуска + перемотка. Часы общие для приложения и воркера и переживают перезапуск; пока стек выключен, время тоже идет. Чтобы начать заново нужно воспользоваться командой `docker compose down -v`.
- Перемотка идет только вперед, не больше года за раз (кнопки «+1 час» и «+1 день», `POST /api/clock/advance`). В тестах часы ручные.
- Все даты указаны в UTC.  Дата без времени = 00:00 UTC.
- «Больше 60 / 30 дней» считаем в календарных днях по UTC, если прайсу ровно 60 дней, он ещe не устарел.  
Пресет «Писали меньше 14 дней назад» и окно ответа считаем по точному времени. Ответ засчитывается, если пришел меньше чем через 14 дней после отправки, а новая отправка в чат возможна через 14 дней и позже. Поэтому в чате всегда открыта не больше одной рассылки.


### Остальные допущения

- `price_updated_at: null` у активного поставщика означает, что прайса нет. Такой поставщик попадает в пресет «Активные, прайс устарел». `last_activity_at: null` у нового — «активности не было», попадает в «Новые без движения».
- В общем чате у всех поставщиков один менеджер. Если это не так, запуск блокируется. 
- Пустое значение в шаблоне — это `null`, пустая строка или одни пробелы. Фигурные скобки в шаблоне нужны только для подстановок: опечатка в подстановке или лишняя скобка также блокируют запуск.
- У поставщика не больше одного чата. Если чатов больше, поставщик исключается с причиной «несколько чатов, админу нужно выбрать вручную».
- Сами сообщения повторно не уходят: правило 14 дней только разрешает писать снова, а рассылку запускает админ.
- Примененное предложение замораживается. Дополнение, пришедшее после применения, это новое предложение, и его тоже можно применить один раз. Защита от двойного применения стоит в базе: отметка ставится условным `UPDATE`, а у записи прайса уникальная ссылка на предложение. Каждое нажатие кнопки «Применить» добавляет запись в историю прайса и обновляет `price_updated_at`.
- Если в общем чате ответила компания, которую в этой рассылке не спрашивали, ее ответ на статусы не влияет (пометку ставим «не по рассылке»).
- Статусов два — `active` и `new`. Поставщик с другим статусом при загрузке пропускается с предупреждением; ссылка чата или контакта на несуществующего поставщика тоже пропускается. Запись без нужного поля или с неверной датой пропускается целиком, с предупреждением.  
- Дата последней отправки позже времени, указанного в задании, ставим ошибка данных: чат исключаем, причину показываем админу.
- Цена диапазоном (от 0.40 до 0.45) для такого случая берем нижнюю границу с пометкой, админ уточняет перед нажатием кнопки «Применить». Когда срок приходит диапазоном, также берем верхнюю границу, тоже с пометкой.
- Сообщения с `t < 0` (написаны до нашего запроса) не считаем за  ответы; `t = 0` считаем за ответ. Точные копии сообщения (тот же чат, отправитель, `t` и текст) отсеиваем.


## Ответы на вопросы

**Как ответ в общем чате привязывается к рассылке и к поставщику.** 

К рассылке привязываемся по чату и времени. Ответ учитывается в течение 14 дней после последней отправки. Пока это окно открыто, новая рассылка в чат не запускается.  
К поставщику привязываемся по нику через `supplier_contacts.json`, без учета регистра. Если в чате один поставщик, привязка происходит автоматически.
Если ник неизвестен, ответ помечается как «непонятно, от какой компании» и не влияет на статусы. Модель предлагает поставщика, а админ подтверждает выбор в отчете.
Если поставщика не было в рассылке, ответ получает пометку «не по рассылке». Сообщения наших аккаунтов игнорируются.

**Что сломается первым, если поставщиков станет в 10 раз больше.**

Первым делом упремся в лимит 100 сообщений в сутки на один аккаунт. Наример, при 500 чатах рассылка растянется на 5 дней, а окно сбора ответов закроется только через 19 дней. При этом `RATE_LIMIT` может остановить всю очередь, а данные чатов за время ожидания к этому моменту могут уже устареть.

**Решение:** несколько аккаунтов для рассылки, повторная проверка чатов перед отправкой и приоритизация очереди.


## Что не успели
Требования, описанные в задании, выполнены полностью. 

## Ограничения

- **`start.sh` на Windows не проверен.** Проверен только на macOS и на Linux. На Windows не запускался.
- **Вложения не читаются.** Цена «во вложении» — только пометка, человек вписывает цену сам.
- **Очередь не перепроверяет чат перед отправкой.** Проверка только при запуске рассылки.
- **`unknown` проверяет админ.** Если воркер упал посреди отправки, сообщение помечается «неизвестно, ушло ли» и повторно не отправляется. Отметить в интерфейсе «ушло» или «отправить снова» нельзя, сверки с историей чата тоже нет: админ проверяет чат и при необходимости пишет руками.
- **Ошибка отправителя, кроме `RATE_LIMIT`,** оставляет сообщение в `sending` до перезапуска воркера. Дубля не будет, но рассылка до перезапуска не завершится. 
- **Ответ с незнакомого ника не меняет статус поставщика.** Админ может выбрать поставщика у предложения и применить его, но статус поставщика в рассылке остается прежним (например, статус «молчит»), а ответ показывается среди непривязанных.
- **Справочники подгружаются один раз.** Загрузка только добавляет новые записи, поэтому правка `data/` после первого запуска заработает только на  чистой базе (`docker compose down -v`).
- **Номер рассылки больше int** в адресе (`/api/campaigns/99999999999`) дает 500 вместо 404.
